# 中英文检索嵌入模型选型建议

> 你的语料是**中英混排的技术笔记 + 架构决策**，且已有强词法通道（TF-IDF/BM25）。
> 选型必须围绕这两点，不是单纯比 MTEB 总分。

## 一、本地现有资产（实测盘点）

| 模型 | 磁盘 | 状态 |
|---|---|---|
| `Qwen3-Embedding-8B`（fp16） | 15 GB | 保留（回滚用） |
| `Qwen3-Embedding-8B-NVFP4` | 4.9 GB | **在跑**（:8081，占 9.9 GB 显存，16K 上下文） |
| `bge-reranker-v2-m3` | 2.2 GB | 已卸载服务（保留文件） |
| `Qwen3-Reranker-4B` | 7.6 GB | 未用 |

## 二、选型的关键洞察：**互补性 > 总分**

现在的检索架构已经有很强的**词法通道**（TF-IDF + BM25 + RRF 融合）。
在这个前提下，嵌入模型只有满足下面之一才值得引入：

- ✅ **提供词法通道拿不到的信号**（如稀疏语义权重、跨语言对齐）
- ❌ **只是"另一路稠密向量"** —— 与现有通道冗余，而实测已证明稠密重排在本库是负收益

这就是 `Qwen3-Embedding-8B` 在本库**屡次失败**的深层原因：它是纯稠密模型，
而本库的瓶颈从来不是"缺一路稠密"，是"**稠密理解不了元数据强信号**"（分层/置信分/同族）。

## 三、推荐：加装 `BAAI/bge-m3`（不替换现有的）

**为什么是它**：

| 特性 | 对本库的价值 |
|---|---|
| **自带 sparse（词法）权重输出** | 与现有 BM25 **正交**，可在 RRF 里当第三路，而不是重复第二路稠密 |
| **100+ 语言统一空间** | 中英混排笔记 + 英文路径/命令，跨语言命中（如查"向量检索"能命中 vector retrieval 笔记） |
| **8192 上下文** | 本库的 CCH 上下文串 + 正文一起嵌入不截断（现模型 16K 更宽，但 bge-m3 够用） |
| **2.2 GB 量级** | 显存开销小（当前空闲 49 GB） |
| 多维输出（dense + sparse + colbert） | 可选三路融合，实验空间大 |

**注意**：官方 MTEB 总分 bge-m3 低于 Qwen3-Embedding-8B（后者在 MTEB multilingual 上更强）。
**但总分不是本库的判据**——本库要的是"与词法通道互补"，这正是 bge-m3 的设计目标
（它本来就是为"稠密+稀疏+多向量"混合检索设计的）。

## 五、可量化判据（避免凭感觉换模型）

| 指标 | 判据 | 测法 |
|---|---|---|
| `recall@10`（30 题黄金集，人工标注应命中的笔记） | 提升 ≥3% 才换 | 对每题的"正确笔记"做标注（需要你参与一次） |
| `canon@K` | **不得下降** | `scripts/eval_retrieval.py` |
| 中文查询命中英文笔记 | 期望有提升 | 手写 5 个跨语言查询对 |
| 单次嵌入延迟 | ≤ 现有（89ms/25 条） | 见 `/tmp/bench_models.py` 的测法 |

## 六、诚实标注（未验证部分）

1. **我没有实测 bge-m3 在本库的表现**——上面是选型论证（基于设计目标与架构分析），
   不是实测结论。要下结论必须跑第四节那套对比。
2. 本库**没有"每题应命中哪些笔记"的标注集**，所以 `recall@10` 目前测不了——
   P4 的 ground truth（30 题草稿）确认后才有 ground truth，
   但那是"答案"级标注，不是"文档"级标注。要严格评估需**再加一轮文档级标注**。
3. 若目标是"提升自指类问题"，`docs/concepts.md`（概念索引）已被实测证明是好得多的手段
   （top1 从 90% → 100%），**优先做这类结构化手段，再考虑换模型**。

## 七、结论

> **不要为了"换个更好的嵌入模型"而换。**
> 本库两次独立实验都指向：稠密通道的瓶颈不在模型强弱，在"它看不懂元数据"。
> 真正有前景的是 **bge-m3 的 sparse 输出**（与 BM25 正交，可当第三路），
> 以及继续强化**结构化手段**（概念索引已见效：top1 90%→100%、top3 67%→90%）。
