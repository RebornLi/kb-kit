# kb-kit 进化回顾与优化方案

> 宗旨：**可以进化的有效知识库** —— 知识不重复、有条理，成为使用者的**第二大脑**。
> 本文按业务环节逐步分析，结合 2025–2026 最新技术给出优化方案。
> **所有结论都有证据**：产物实测 / 受控实验 / 带链接的文献。推断会明确标注。

---

## 一、方法论

| 证据类型 | 做法 | 回答什么 |
|---|---|---|
| 代码规模 | 按环节统计模块数/行数 | 力气花在哪 |
| **产物证据** | 查生产库该环节的产物是否存在、多大、多久没更新 | 该环节**是否真的在工作** |
| **受控实验** | 真实库副本上对比方案的质量/延迟 | 改动**是否真的更好** |
| 文献对照 | 4 份 2025–2026 技术调研（含一手链接） | 别人踩过的坑 |

第三类最关键 —— 本项目已有**三次**"看起来该改、实测改了更差"的先例，所以任何排序类改动
必须先过黄金集；而黄金集本身有局限（§4.2），需要独立探针补齐。

- **S8 治理**：巡检/schema/审计齐全，每日在跑。**良好**。
- **S9 反馈/进化**：**26% 代码、零动作**（§3.1）。

|---|---|---|

| L1 检索修正 | `kb_retrieval_adjust.json` | **不存在** |
| L1 缺口提案 | `.kb_adaptretrieve_proposals.jsonl` | **不存在** |

而同时 `feedback_state.json` 已积累 **2,039 个查询会话 / 1,407 条命中记录**。
**原料在堆积，加工厂从未开工。**

### 3.2 原因不是坏了，是**没接线**

生产库 02:00–02:04 实际运行的脚本，及其调用的命令：

| 脚本 | 命令 |
|---|---|
| `growth_cron.sh` | `kb link apply` |
| `kb-curate.sh` | `kb curate run` / `review` |
| `kb-daily-supervisor.sh` | `kb query` |
| `kb-verify-cron.sh` | `kb verify` |
| `healthcheck_cron.sh` / `backup_now.sh` / `drill_now.sh` | 巡检 / 备份 |

**`kb feedback`、`retriage`、`adaptretrieve`、`selfweight`、`meta`、`l4`、`l5`、`recall`、
`audit`、`tagfix`、`contradiction`、`drift`、`rsi` —— 一个都没被调度。**
（调度器配置读不到：无 user crontab、无 systemd timer；但日志证明 02:00 确有任务在跑，
定义位置需人工确认。）

### 3.3 反复问同一问题的信号**极度充足**却没被利用

2,039 次查询只有 **382 个不同问题（5.3× 重复）**：

| 查询 | 次数 |
|---|---|
| 知识结晶 正典 是什么 | **73** |
| vLLM 部署有哪些坑 | **68** |
| OpenClaw 失忆 embedding 服务排查 | **56** |

L1 缺口检测的前提正是"同一 query 短期再问 = 上次没答上"。**信号溢出，却零提案。**

### 3.4 投入与价值倒挂

- 26% 代码在自我调节 → 实测**零动作**；
- 1% 代码在复习 → 实测**零使用**；
- 而"第二大脑"的痛点是**找到记过的知识**（检索）、**不重复**（去重）、**有条理**（连接）
  —— 三者约 16% 代码，其中连接仅 1.7%。

**→ 优化重点应是：(a) 把已有信号接进调度、(b) 补齐面向用户的检索/去重/连接能力，
而不是再造自调机制。**

### 3.5 已有能力被"默认关闭"埋没

| 能力 | 状态 |
|---|---|
| embedding 端点 | ✅ 可用（qwen3-embedding，**4096 维**，直连实测通过） |
| cross-encoder 重排 | ⚠️ 端点 :8082 **未运行** |
| embedding 重排 | ⚠️ 可用但 `KB_RERANK` 默认 `0`；实测作"替换排序"是**负增益**（§4.1） |
| **索引里的向量** | ❌ **一个都没存** |

## 四、受控实验

### 4.1 语义重排：作为"替换排序"是负增益（复测确认既有结论）

30 题黄金集（禁缓存）：

| 方案 | top1 | recall@4 | recall@10 | MRR | p50 |
|---|---|---|---|---|---|
| 基线 `KB_RERANK=0` | **90.0%** | **82.5%** | 98.3% | **0.950** | **146 ms** |
| `KB_RERANK=embed`（替换） | 86.7% | 80.0% | 98.3% | 0.933 | 849 ms |

与代码注释里 2026-10-01 的既有实测同向（cross-encoder 曾让 top1 90%→70%）。
**根因**：首段排序靠元数据强信号（tags/kb_summary/标题/分层），纯文本语义重排会覆盖它。
文献亦印证：本库三次独立实验（bi-encoder / cross-encoder / LLM）**全部有害**
（LLM 重排 top1 100%→73%，21.8s/查询）。

### 4.2 黄金集的**方法论局限**

`gold_candidates.jsonl` 的 `sources` 是**用同一套检索**生成的 → 结构上测不出
"笔记记过、但查询用词与原笔记不重合"。它的 `recall@10=98.3%` 只说明"词法可达范围内几乎没漏"。

### 4.3 独立探针：改写式查询下的语义缺口（**决定性证据**）

`tests/probe_semantic_gap.py`：让本地 chat 模型就某篇笔记写一条"**换措辞、不复用原文关键词**"
的问题，再分别用词法检索与稠密最近邻找该笔记（top-10，16 题）：

| 通道 | 命中源笔记 |
|---|---|
| 纯词法（现状） | **6/16 = 38%** |
| 稠密向量 | **15/16 = 94%** |
| **仅稠密能找回** | **10 篇（62%）** |
| 仅词法能找回 | 1 篇 |

典型例子（词法失败、稠密成功）：
> q:「在某种 AI 芯片上运行文本生成视频模型时，采用哪套软件框架配合权重压缩方案最为合适？」
> → 命中 `MiniMaxH3视频模型部署ComfyUI...NVFP4`（查询与标题**零词面重合**）

**→ 结论：kb-kit 的排序没问题（元数据信号很强），召回有大问题（词汇不匹配就找不到）。
稠密通道应作"补召回"，绝不能作"替换排序"。**

这与调研的关键数据吻合：DynamicMem 显示 **>93% 的失败归因于检索而非作答模型**。

## 五、技术对照（2025–2026）

四份调研已落盘：`docs/retrieval-tech-2025-2026.md`、`docs/research/agent-memory-2025-2026.md`、
`docs/research/dedup-conflict-drift-2025-2026.md`（复习与 PKM 见 §5.5）。
标注：**(A)** 纯 stdlib · **(B)** 需已配置的本地模型 · **(C)** 需新依赖（本项目一律不引入）。

### 5.1 检索：该做什么、不该做什么

| 事项 | 文献结论 | 归类 | kb-kit 策略 |
|---|---|---|---|
| 结构化/元数据信号 | 收益 > 任何模型通道（本库实测：分层降级 top1 正典率 50%→97%） | A | **保持并加强** |
| RRF 融合 | k 需扫参（10/20/60）；凸组合常优于 RRF（[2210.11934](https://arxiv.org/abs/2210.11934)） | A | 加 k 扫参实验 |
| **稠密通道** | — | B | **本项目实测缺口 62%（§4.3）→ 做补召回** |
| Contextual Retrieval | 失败率 −35%/−49%/−67%，$1.02/M tokens（Anthropic） | B | **已有确定性 CCH 但从未单独量化 → 补测** |
| Late chunking | 本机 vLLM 有 token 级向量 → 归 B；短笔记增益小 | B | 长笔记子集做 A/B |
| 语义切分 | 开销未被一致增益证明（[2410.13070](https://arxiv.org/abs/2410.13070)） | A | 不改 |
| **RAPTOR / GraphRAG** | 成本全在索引；微软自家 LazyGraphRAG 把索引成本压到 **0.1%** | B/C | **不做**（1500 篇不划算） |
| **LLM / cross-encoder 重排** | 本库三次实验全有害 + 文献增益仅 +2–8 nDCG@10 | B | **不做**（保持默认关） |
| 查询改写/分解/HyDE | 改写会漂移（[10.1145/3805712.3809721](https://dl.acm.org/doi/10.1145/3805712.3809721)） | B | 只做"原查询 ∥ 改写并行"，不替换 |
| 评估 | 配对 bootstrap + Holm 校正；**n=30 只信 ≥5pp 差异** | A | 采纳 |

### 5.2 记忆：最高杠杆是**双时态字段**，不是图库

- Zep/Graphiti 的价值来自 `tvalid/tinvalid`（事件时间 vs 记录时间）**语义**，不是图引擎
  （[2501.13956](https://arxiv.org/abs/2501.13956)）→ **frontmatter 加字段即可，无需 Neo4j/向量库**。
- 去重边际收益被高估：6 种策略实测总分落在 0.895–0.907 极窄带，纯 Add-Only 反而最高；
  而 Mem0 式朴素四操作有明确失败模式（把相关但不矛盾的两条判为矛盾并删掉前者）
  （[2504.19413](https://arxiv.org/abs/2504.19413)、[2508.19828](https://arxiv.org/html/2508.19828v1)）。
  → **≥0.95 只标记候选，0.85–0.95 交人工/阶梯裁决，绝不自动合并**。
- **睡眠时计算**（[2504.13171](https://arxiv.org/abs/2504.13171)）：空闲期预计算，同等精度省 ~5× test-time 算力；
  效力与"查询可预测性"强相关 —— 本库查询集中（382 个问题重复 5.3×），**收益预期乐观**。
- Letta MemGPT 2.0 的「只读主流程 + 有写权限的整理流程」正是 L1–L5 阶梯的**组织学依据**。

### 5.3 摄入与分块

- 质量门禁三态 **pass / quarantine+flag / reject**：reject 只留给不变量（无 `source_ref`、
  schema 缺失、空正文）；个人库**误拒不可恢复、误收可挽回** → 宁入库不拒。
- 结构元素切分优于滑窗（[2402.05131](https://arxiv.org/abs/2402.05131)）；语义切分不做。
- **LLM 回灌污染防护**：LLM 产物强制 `derived=true` + 必须挂 ≥1 条非 LLM `source_ref`；
  记录 `generator/model/version`；检索对 tier=5 降权。实证风险：2025 年中约 **35%** 新网页为 AI 生成，
  AI 文本语义相似度高 **33%**（[2604.26965](https://arxiv.org/abs/2604.26965)）。

### 5.4 去重与建链

- MinHash 现实现每 shingle 做 **64 次**线性置换（4500 篇 ≈ 5.8 亿次纯 Python 算术）→
  换 **bottom-k（KMV）**：每 shingle **1 次** `blake2b`，哈希量降 ~64×，且去掉线性置换的独立性偏差。
- 候选对加 **size filter**（Jaccard≥t ⇒ 长度比≥t）；用 **containment** 区分"重复片段"与"重复笔记"。
- 阈值**不可跨模型迁移** → 必须本地 200 对标注标定（现有 `_SIM_THRESHOLD=0.55` 与降级 `0.22` 偏松）。
- 冲突判定要先过**槽位 + 时间重叠**闸：同 (主体, 关系) 且 `valid` 区间相交、值不同才是矛盾；
  区间不交就是**时序更新**（双时态）。LLM 判矛盾需**双调用**（solve + verify），
  实测单调用有 **63–76%** 概率漏掉注入的矛盾（[2609.05928](https://arxiv.org/abs/2609.05928)）。
- 建链要 **≥2 个独立信号**且必须含"同源/共引/标签"之一 —— 误链沿图传播，漏链近乎零成本
  （[KG Refinement](https://dl.acm.org/doi/abs/10.3233/SW-160218)）。

### 5.5 复习与知识组织

- **SM-2 → FSRS-6**：公式与 21 个公开默认参数已逐字核对（`fsrs-rs/model_v6.rs`、`dart_srs`、`py-fsrs`）。
  `S` 的定义是"R 降到 90% 所需天数"→ **现有 `interval` 可直接当 S 初值**，迁移约 150 行 stdlib。
- **⚠️ 现有 `GRADE_Q={again:1,hard:3,good:4,easy:5}` 是 SM-2 语义，FSRS 只认 1/2/3/4** ——
  不重映射会让难度 D **反向更新**（这是本轮发现的一个确定性正确性问题）。
- **整篇笔记不该进 SRS**（Matuschak 五判据）：笔记级复习的正确定位是 **salience（保持想法在视线内）**，
  而这种用途下**不该用"忘了/记住了"调调度** → 反证 kb-kit 现有 `importance × overdue` 排序是**对的**。
- 组织方法论：有证据的是 **PIM（re-finding 靠检索与上下文线索，不靠分类树）** →
  「检索质量 + 时间/来源/domain 元数据」比分类树更决定可检索性；MOC 是唯一有据可依的图谱用途。
- **抗 Goodhart 的健康指标（≤5 个，全部 A）**：① 两跳可达覆盖率 ② 检索一次命中率
  ③ 预测校准（Brier）④ 陈旧率 ⑤ 复用率（在产出物中被引用次数）。
  易刷指标（笔记数/字数/链接数/复习次数）**只作诊断不作 KPI**。

## 六、优化方案（按性价比排序）

### P0 · 立即可做，证据最强

| # | 动作 | 类别 | 预期 | 为什么排最前 |
|---|---|---|---|---|
| **1** | **语义补召回通道**：索引存降维量化向量，查询时与词法结果 RRF 融合（**只补召回，不替换排序**） | A+B | 改写式查询命中 38%→**90%+**；黄金集**不得回退** | §4.3 实测缺口 62%；且 >93% 失败归因检索 |
| **2** | **修 `recall_schedule.GRADE_Q` 映射**为 1/2/3/4 | A | 修正确定性缺陷 | FSRS 语义不匹配会让 D 反向更新 |
| **3** | **`dedup` 换 bottom-k MinHash**（+ size filter + containment） | A | 哈希量 **-64×**；候选更准 | 纯性能与精度，行为兼容 |
| **4** | **把 L1 接进调度**：`kb feedback ingest` + `kb adaptretrieve propose` 加入 cron | A | 让 5.3× 重复信号开始产出提案 | 26% 代码零动作的根因就是没接线 |

### 7.1 P0#1 语义补召回通道 ✅

**设计**（`pipeline/dense.py` + `rag.py`，`IDX_VERSION = 8`）：

1. **稀疏随机投影降维** 4096 → 256（Li et al. 2006 very sparse RP，固定种子可复现）。
   原始向量 25 MB → **1.6 MB**；投影矩阵 16,384 个非零。
2. 向量存进索引（与词法同生共死）；增量索引**复用未变文档的旧向量**（改一篇只调 1 次端点）。
3. 查询时 **尾部槽位填充**（`DENSE_SLOTS_FRAC = 0.4`）：词法前 60% 名次**按构造不变**，
   其余槽位给"稠密-only"笔记。
4. best-effort：端点不可用/超时/异常 → 静默缺席，检索退回纯词法。

**为什么不是 RRF 融合**（实测，30 题黄金集）：加权 RRF 单调变差 ——
`w=0.3` top1 90.0%→83.3%、rec@4 82.5%→65.0%；`w=0.5` top1 76.7%；`w=1.0` top1 60.0%。
与"语义重排"同因：**稠密名次混进头部会顶掉元数据强信号**（这是本项目第 4 次同款教训）。
改成预留槽位后头部位移为 **0**（不是"权重小所以影响小"，而是"按构造没动"）。

**双指标实测**：

### 7.22 插件系统优化：只读命令进程内快路径 ✅

**背景**：35 个 KB 模块插件全部走 `SubprocessPlugin` —— 每个命令都 `subprocess.run([python,
脚本.py, ...])`，即「启动器进程 + 脚本进程」双进程。对高频只读命令这是纯开销。

**实测开销拆解**（`kb query` 冷缓存，墙钟）：

| 阶段 | 耗时 |
|---|---|
| 解释器启动 + 插件发现（39 个模块） | ~15ms（发现本身仅 3ms） |
| **子进程 spawn rag.py（双进程开销）** | **~40ms** |
| 索引加载（pickle 9.2MB） | 72ms |
| 查询计算 | 62ms |

→ 子进程开销占端到端 **~21%**（150ms → 无子进程约 115ms）。

**优化**：`SubprocessPlugin` 增加 `IN_PROCESS_ACTIONS` 白名单（按 action），只对**只读**命令
开启进程内执行（`import 模块 + main()`），写命令永远走 subprocess 隔离。安全保证：

- import 失败 / 无 main() → 回退 subprocess（无副作用）；
- main() 抛异常 → 丢弃已捕获输出、回退 subprocess；
- stdout/stderr 全程捕获、成功才回放（杜绝双份输出）；
- 静态护栏：写动作（index/apply/mark/fix/bitemporal/decay）不得进白名单。

**已开启的只读命令**：`query`、`recall deck/status`、`schema check/fields`、`gate check`、
`validate`、`healthcheck`、`audit scan/log`、`confidence show/audit`（8 个插件）。

**验证**：query 输出与子进程**逐字节一致**（命中路径/meta/adjustments 全等）；端到端墙钟
150→**~125ms**；287 测试全绿；新增 `InProcessPluginTest`（4 条）钉住「进程内==子进程」与
「写动作不进白名单」。

### 7.23 kb-context-dsh / kb-context-hook 优化：常驻查询 worker ✅

**背景**：两个上下文钩子（DSH cordis 插件 + OpenClaw 插件）之前每轮用户对话都
`execFile('python3', ['rag.py','query',...])` —— 每次 spawn 全新 Python 进程，重新付一遍
解释器启动(~30ms) + import(~30ms) + **9.2MB 索引 pickle 加载(~72ms)**，纯开销 ~130ms/查询，
而打分本身只要 ~60ms。

**优化（新技术 = 常驻 retriever + 索引 mtime 失效）**：

1. **`pipeline/kb_worker.py`**（kb-kit 侧，随库分发）：常驻 worker，索引**加载一次**、
   文件 mtime 变了才重载（cron 重建索引后下一查询自动拿新索引）。JSON-lines over stdio
   协议，单条失败只回 `{ok:false}` 绝不退出。
2. **`worker.js` / `worker.mjs`**（两插件各一份）：懒 spawn、请求序列化、按 seq 匹配响应
   （兼容不回显 seq 的旧 worker 时退化为 FIFO）、崩溃/EOF 自动回退逐次 execFile。
3. **片段质量**：命中自带的 `context`（父子块/CCH 上下文）优先于原始 snippet；默认截断
   **40→140 字**（40 字不够模型判断相关性）；并修掉一个**真 bug** —— 字节封顶初版只累计
   命中行、没算前缀+围栏+免责说明，导致整块超预算 ~23 字节。

**实测**：稳态单查 **~190ms → ~60ms（约 3×）**；3 次连续查询 175ms；worker 与回退路径
输出一致。kb-kit 287 测试全绿；DSH 插件 27/29（2 个失败是测试环境无 vault 的既有问题）；
hook 测试全过。
