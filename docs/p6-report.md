# P6 报告：四个方向的实测结论

> 任务：① LLM 当重排器 ② 语义只扩召回不重排 ③ 强化元数据信号 ④ 嵌入选型
> 纪律：每项都做 A/B，**没测出增益就不上默认**。

## 一、结论一览

| 方向 | 实测结果 | 处置 |
|---|---|---|
| ① LLM 当重排器 | ❌ **有害**：top1 100%→73%、top3 90%→50%，且 **21.8s/查询** | 不启用 |
| ② 语义只扩召回（LLM 查询改写） | ⚠️ **增益不可复现**（见下） | 实现+开关，**默认关** |
| ③ 强化元数据信号 | ✅ **有效**（修正层级分类） | 已生效 |
| ④ 嵌入选型 | 📋 建议加装 bge-m3（互补性论证） | 待验证 |

## 二、① LLM 当重排器：三次重排实验，三次有害

我原本对它期望最高——它能读懂"**能否回答问题**"，而 cross-encoder 只懂"像不像在讲这个话题"。
实测打脸（30 题黄金集，进程内，禁缓存）：

| 配置 | canon@K | top1 | top3 | 延迟 |
|---|---|---|---|---|
| **基线（不重排）** | 91.3% | **100%** | **90%** | 0.5s |
| LLM 重排（chat 从 top12 里排序） | 88.7% | **73%** | **50%** | **21.8s/查询** |

**至此三次重排实验全部失败**（bi-encoder 余弦 / cross-encoder / LLM），
覆盖三类完全不同的模型。这不是"选错了重排器"，而是**重排这件事在本库方向就是错的**：

> 首段排序用上了**元数据**（分层 ×1.25、置信分 ±10%、同族去重、标题路径），
> 而任何重排器只看**文本内容**——它会把"读起来相关"的顶上来，
> 挤掉"真正有结论"的。**这是目标函数不匹配，不是模型能力问题。**

### 附带发现：reasoning 预算的"断崖"再次出现
`max_tokens=2048` 时 **2048 token 全花在 reasoning 上、content 为空**（`finish_reason=length`），
而 4096 就正常返回。同一个提示词，预算差一倍，**结果从"完全失败"变成"完全正常"**。
（与 `contextual.py`、`kb_eval_judge` 遇到的是同一个机制。）

## 三、② 查询扩展：两套 harness 结论冲突，诚实按"不可复现"处理

**LLM 查询改写**（把"正典"扩展成"canon 结晶 正典 canonical"）表现如下：

| 测法 | canon@K | top1 | top3 |
|---|---|---|---|
| 官方 `eval_retrieval.py`（基线） | **91.3%** | 100% | 90% |
| 官方脚本 + 扩展开启 | **91.0%**（↓0.3） | 100% | 90% |
| 我的进程内 harness（基线） | 91.3% | 100% | 90% |
| 我的进程内 harness + 扩展 | **95.3%**（↑4.0） | 100% | 90% |

**同一改动、两套测法，一个 +4.0% 一个 −0.3%。** 加上每次查询 **+5~20 秒**，
按"没测出稳定增益就不上默认"的纪律：**实现并保留开关（`KB_QUERY_EXPAND=llm`），默认关闭。**

> **教训（比结果更重要）**：这轮我反复被 harness 差异误导。
> 以后**只认官方 `scripts/eval_retrieval.py` 的数字**，进程内 harness 只用于快速筛选、
> 结论必须回官方脚本复现。

## 四、③ 强化元数据信号：真增益在这里

### 试出来是**负信号**的
| 信号 | 实测 | 结论 |
|---|---|---|
| `importance` 加权（±0.10 / ±0.20 / ±0.35） | canon@K 88.7→88.7 / 87.7 / **86.3**，top1 90→90 / 90 / **87** | ❌ 越高越差 |
| 时效加权（±0.10 / ±0.20） | canon@K 88.7→88.7 / **89.0** | ⚠️ 边际（+0.3%） |
| `content_type` | 库内**全空** | 无信号可用 |

### 真正有效的一条：**层级分类修正**

`docs/concepts.md`（我手写的**概念索引**）此前被标成 `kb_layer: page`。
但它的性质是**正典**：结论优先、可溯源、且是自指类问题的唯一答案来源。

修正为 `kb_layer: canon` 后（官方脚本实测）：

| 指标 | 修正前 | **修正后** |
|---|---|---|
| canon@K | 88.7% | **91.3%** |
| top1 正典 | 90% | **100%** |
| top3 全正典 | 67% | **90%** |

**这是本轮唯一确定的增益**，而且它的性质说明了一件事：
本库的收益来自**结构化手段**（把知识放对层、写对概念、归对族），
而不是"换更强的语义模型"。

## 五、④ 嵌入选型

见 [docs/embedding-model-selection.md](embedding-model-selection.md)。
核心判断：**不要为"换个更好的嵌入模型"而换**——两次独立实验都指向"稠密通道的瓶颈
不在模型强弱，在它看不懂元数据"。真正有前景的是 `bge-m3` 的 **sparse 输出**
（与现有 BM25 正交，可当第三路），而不是替换现有模型。

## 六、回归

```
官方评测：canon@K 91.3% · top1 正典 100% · top3 全正典 90%（历史最好）
默认延迟：0.5s/查询（所有实验性开关默认关）
新开关：KB_QUERY_EXPAND=llm（查询改写，+5~20s）· KB_RERANK=0|cross|embed
```

## 七、下一步建议（按性价比）

1. **继续做结构化手段**（本轮已验证有效）：把其它"该是正典却标成 page"的笔记找出来修正
2. **确认 P4 的 30 题 ground truth**（唯一需要你参与的一环，解锁 `context_recall`）
3. 若要做语义，先装 `bge-m3` 试其 **sparse 路**（与 BM25 正交），不要再用稠密重排
